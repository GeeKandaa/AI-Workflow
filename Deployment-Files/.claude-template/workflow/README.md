# AI plan workflow — human guide

A Claude Code template for plan-driven work across git worktrees. Every change is planned, implemented,
accepted by you and committed through one lifecycle. A local web UI (or you, in a terminal) runs the human
gates. Headless Claude Code sessions do the work in each phase.

## Requirements

- Claude Code, started from the workspace root (the folder holding `CLAUDE.md`).
- Node.js 18+ on `PATH` (the CLI is dependency-free `.mjs`).
- git. Each immediate sub-folder of the root containing `.git` is a worktree, named after its folder. That
  includes `git worktree add` checkouts, whose `.git` is a file. Extra entries go in `config.json → repositories.map`.

## Roles

| Who | Commands |
|---|---|
| AI (headless phase sessions) | `new`, `validate`, `normalise`, `overlaps`, `note`, `deviate`, `complete`, `archive-finish`, `archive-abort`, `status`, `repos` |
| Human / UI (gates) | `stage`, `continue`, `cancel`, `rework --feedback "…"`, `archive-begin [options]`, `merge <into> <plan…>`, `unmerge <plan>` |

`settings.json` denies the gate commands, and git writes, to the AI's Bash and PowerShell tools. The rules
match by prefix, so they stop accidents, not a determined workaround. The UI runs gates from its own process,
so the rules don't affect it.

## Phase prompts (`.claude/commands/`)

The UI starts a headless session per phase, for example `claude -p "/plan-implement my-plan"`:

| After the UI ran | Prompt | AI does |
|---|---|---|
| — | `/plan-new <description>` | investigates, writes and validates the plan |
| — | `/plan-amend <plan> <instructions>` | revises a plan in planning (e.g. with answers to its questions) and validates it |
| `stage` | `/plan-implement <plan>` | implements, then `complete` |
| `continue [--decision "…"]` | `/plan-continue <plan>` | carries on with the approved deviation, following the human's chosen option |
| `rework --feedback` | `/plan-rework <plan>` | addresses the feedback, then `complete` |
| `cancel` | `/plan-cancel <plan>` | writes the Plan Extension for the remaining work |
| `archive-begin` | `/plan-archive <plan>` | reconciles other plans, then `archive-finish` |
| `merge <into> <plan…>` | `/plan-merge <into>` | folds the merged plans' brief, testing, files and commits into `<into>` |

`plan.mjs status --json` gives the UI every active plan: status, worktrees, files, overlaps, pending deviation,
open questions, history, and the archive lock.

Questions for the human go in the plan's `## Outstanding Questions` section, so they're easy to find. `validate`
counts them, and `stage` warns if any are unanswered but doesn't refuse: approving anyway leaves them to the AI's
judgement.

## Several plans per worktree

- **Stage**: refused if another *staged* plan lists any of the same files. Overlaps with plans in planning or
  confirmation are only noted.
- **Complete / archive**: a changed file this plan doesn't list but another active plan does is attributed to that
  plan and left alone. Only changes that *no* plan lists count as "unlisted". If Files Affected grew into another
  staged plan's files, `complete` records that under AI Feedback.
- **Archive**: `archive-begin` and `overlaps` list the shared files and their uncommitted state. The archiving plan
  commits shared files **whole**. The AI updates the other plan (or aborts and explains if the other plan's edits
  aren't ready) and records the decision in both plans.
- **Branches**: `stage` records each worktree's checked-out branch in the plan's front-matter (`branches:`) and
  refuses a detached HEAD. `complete`, `rework`, `archive-begin` and `archive-finish` refuse if a worktree has
  switched branch or is detached, so commits always land on the branch the plan was approved for. Worktrees added
  to Files Affected during implementation are recorded at `complete`. The Archive Record lists the branches.
- **Archive lock**: one archival at a time across the workspace. The lock file is created atomically, so of
  several simultaneous `archive-begin` calls (a double-click in the UI, say) exactly one wins.
- **Generated files** (lockfiles, generated code, snapshots, committed build output) are listed in Files Affected
  like any other, noted `— generated by <command>`. The AI predicts them from `docs/` while planning. At
  `complete`, unlisted changes block with guidance on adding generated ones, and unlisted changes in worktrees the
  plan doesn't list are warned about.
- **Merging**: when plans can't sensibly be archived one at a time (two plans in confirmation editing the same
  file, say), the human merges them: `merge <into> <plan…>` (all in planning, or all in confirmation). The merged
  plans get `merged_into:` and stay in `plans/`. They're left out of overlaps and claims, and every gate refuses
  them. `/plan-merge <into>` folds them into `<into>`. `archive-begin` refuses until `<into>` lists every file the
  merged plans list, and `archive-finish` archives them alongside it, with an Archive Record that points at
  `<into>`'s commits. Merging into an already archived plan archives the plans at once with that note, for
  example a plan left behind after its partner was archived. `unmerge <plan>` undoes a merge before archival.
- Committing individual hunks of a shared file isn't supported. Sequence the plans, or commit by hand and use
  `--manual-commit`.

## Archive options (`archive-begin <plan> …`)

- `--allow-unlisted` leaves uncommitted changes that no plan lists in place and archives anyway. They're
  recorded in the Archive Record. `config.json → archive.allowUnlistedByDefault: true` makes this the default,
  and `--require-listed` restores the strict check for one archival.
- `--manual-commit [<hash> | <worktree>=<hash> ...]`: you committed the work yourself. The workflow makes no git
  write and only records the commits. A worktree given no hash is recorded as `MISSING`, and a commit touching none
  of the plan's files gets a warning. This can't be combined with `--allow-unlisted`.

The working tree is checked before the lock is taken. A refusal lists the offending files by worktree, with the
exact commands to choose from.

## Plan layout (canonical order, enforced)

```
---  front-matter (managed by plan.mjs: status, attempt, history, commit SHAs)  ---
# Title
## Brief
## Plan Extension 1 — <date>      (one per cancellation)
## Outstanding Questions          (numbered questions for the human, or "None."; optional in older plans)
## Testing
## AI Feedback                    (deviations, decisions, rework feedback, overlap reconciliation)
## Files Affected                 ### <worktree> → bullets
## Commit Messages                ### <worktree> → fenced message(s)
## Archive Record                 (archived plans only; generated by archive-finish)
```

## Configuration

- `config.json`: directories, archive prefix, `archive.allowUnlistedByDefault`, worktree discovery, commit
  message rules (pattern, lengths, required trailers).
- `commit-template.txt`: the house style shown to the AI. Keep it in step with `config.json → commit`.
- `plan-template.md`: the skeleton for new plans.
