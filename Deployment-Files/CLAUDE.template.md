# AI Plan Workflow

This workspace root holds one project, and each sub-folder is a **git worktree** of it (`### <worktree>` in plans).
Code work is organised as plans in `plans/`. A local web UI shows the plans and runs each phase as a headless
Claude Code session. You do the work; the human approves through the UI.

State changes go through the CLI, run from the workspace root:

```
node .claude/workflow/plan.mjs <command> ...      # `help` lists every command
```

## Lifecycle

```
planning ──stage──▶ staged ──complete──▶ confirmation ──archive-begin → archive-finish──▶ archived
    ▲                 │  ▲                    │
    └─────cancel──────┘  └──────rework────────┘
    ▲                                         │
    └─────────────────cancel──────────────────┘
```

**Human gates**: `stage`, `continue`, `cancel`, `rework`, `archive-begin`, `merge` and `unmerge` belong to the
human. The UI runs them, or the human runs them in their own terminal. Never run them yourself; they are denied in
`settings.json`. When one is needed, say which one and stop. If two plans can't be archived separately (for
example, both in confirmation editing the same file), suggest that the human merges one into the other.

**Merged plans** carry `merged_into: <plan>`. They are archived with that plan, so never edit, implement or
archive them on their own; `/plan-merge <plan>` folds them into the plan they were merged into.

## Planning

1. Investigate. Don't change code for a plan that hasn't been staged. Read the project documentation in `docs/`
   (if any) for build, code-generation and packaging conventions.
2. `plan.mjs repos` lists the worktree names. `plan.mjs new <slug> --title "<title>"`, then replace every `<!-- TODO -->`:
   - **Brief**: why, what, how (file by file, in order), risks, assumptions, out of scope.
   - **Outstanding Questions**: every question for the human, numbered, with options and your recommendation, or
     `None.`. Keep them here rather than in the Brief. When the human answers one, record the decision in the
     Brief (or the latest Plan Extension) and remove the question.
   - **Testing**: numbered verification steps, or `N/A — <reason>`.
   - **Files Affected**: `### <worktree>` headings, one bullet per file: `` - `path/in/worktree` — note ``.
     Include files the work will regenerate (lockfiles, generated code, migrations, snapshots, committed build
     output), noted `— generated by <command>`, using `docs/` and the project's tooling to predict them.
   - **Commit Messages**: `### <worktree>` headings, fenced messages following
     `.claude/workflow/commit-template.txt` (rules in `config.json → commit`). For several commits in one
     worktree, put a bullet list of that commit's files above each message.
3. `plan.mjs validate <slug>` until it passes. If it reports files shared with other plans, address them in the
   Brief. Summarise the plan for the human and stop.

## Implementation (`staged`)

- Implement what the plan describes. Several plans can be staged in one worktree as long as they don't list the
  same files, so touch only this plan's files.
- Stay on the branch the plan was staged on (recorded under `branches:`). Never switch or detach a worktree's
  branch; `complete` and archival refuse if it changed.
- **Minor deviation** (an extra helper, a renamed symbol, one more file that clearly belongs to the change):
  `plan.mjs note <plan> "<what and why>"` and carry on.
- **Substantial deviation** (a different approach, wider scope, a public API, schema or behaviour change, a data
  migration, deleting files that weren't planned): `plan.mjs deviate <plan> "<what, why, impact>"`, explain it and
  stop until the human runs `continue` or `cancel`. If there are alternatives, put them in the deviate text as
  numbered options with your recommendation, so the human can approve with a choice (`continue --decision`).
  After approval, a recorded **Human's decision** overrides your recommendation.
- Finish by making Files Affected and Commit Messages match the work actually done, then run
  `plan.mjs complete <plan>`. Changes that other active plans list are attributed to those plans and don't block.
- If `complete` reports changes no plan lists, work out where each came from. A file your work generated (a
  build, code generator, package manager or formatter) belongs to this plan: add it to Files Affected as
  `— generated by <command>`, add it to the right commit, and `note` it. Build output that shouldn't be committed
  stays unlisted: tell the human it probably belongs in `.gitignore`. Use `--allow-unlisted` only for changes
  that aren't from this plan's work, and say which. If `docs/` didn't predict a generated file, say so in your
  summary so the human can document it.
  Summarise the work and how to test it, then stop.

## After a cancel

`cancel` adds `## Plan Extension N` and marks Testing, Files Affected and Commit Messages with TODOs. Write the
extension (state of implementation, what is left, and the approach), update those sections for the remaining
work, `validate`, and stop.

## Archival (after the human's `archive-begin`)

1. `plan.mjs overlaps <plan>`. Review every other active plan and update anything this work affects. Edit plan
   bodies only.
2. Shared files are committed **whole** by the plan being archived. If another plan's edits in a shared file
   aren't ready, run `archive-abort <plan>` and explain the conflict. Otherwise update the other plan and record
   the decision in both plans' AI Feedback.
3. `plan.mjs archive-finish <plan> --plans-reviewed`. This commits the listed files with the planned messages and
   moves the plan to `plans/archive/`. If it fails before committing, run `archive-abort <plan>` and report.

## Rules

- Don't edit plan front-matter or archived plans. Create plan files only with `plan.mjs new`; don't move or
  delete them yourself.
- Read-only git is fine. Don't commit, push, reset, check out or otherwise write to git: commits come only from
  `archive-finish`, and nothing is pushed.
- Ask before editing `.claude/**` or this file.
